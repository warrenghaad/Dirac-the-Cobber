Yes. I’d make one important change before freezing these three deliverables:

**The Librarian should not be specialized around “Figma templates.” Its domain should be visual grammars, with Figma as its first major source and output adapter.**

That gives it enough breadth to learn a workflow template, an affinity map, UML, ZUI, database matrix, drawing system, or animation without forcing all of them through “screen design” logic. This fits the existing architecture, where Nash Room hosts multiple coordinated viewers and GraphNode, Matrix, Polytope, Workflow Composer, Preview, and Figma Bridge are different projections over shared semantic objects.  

It also preserves the more important Polytope rule: **the visualization is a projection over underlying information, not the underlying truth itself.** 

Here are the first three actual project artifacts.

# Deliverable 1 — Figma Librarian Product Brief

## Working Name

**Prism Librarian**

Alternative internal name:

**Visual Grammar Librarian**

The product may remain colloquially known as the Figma Librarian, but its architecture must not assume that Figma is the only source, representation, or output environment.

---

## 1. Product Purpose

Prism Librarian is an agent-assisted visual intelligence system that:

1. ingests templates, components, diagrams, visualizations, design systems, and examples;
2. decomposes those examples into reusable visual grammar;
3. stores components and template patterns as a governed library;
4. translates semantic requests into visual structures;
5. recommends or composes appropriate visual grammars;
6. produces auditable visual build plans;
7. exports approved plans to Figma and later other rendering environments;
8. learns from human corrections without silently rewriting canonical design rules.

The Librarian is **not** primarily a drawing tool.

It is a:

* library
* pattern recognizer
* design grammar extractor
* visual translator
* visual planning engine
* component recommender
* template composer
* provenance system

---

# 2. Core Product Thesis

A sufficiently structured visual artifact contains recoverable design logic.

That logic can be represented as relationships among:

* semantic purpose;
* hierarchy;
* layout;
* visual encoding;
* component anatomy;
* navigation or interaction;
* grouping;
* sequence;
* scale;
* motion;
* spatial organization;
* data structure;
* user action;
* constraints.

Therefore:

> A template should not be stored only as a file. It should be converted into a reusable description of why its organization works, what structural problem it solves, and under what conditions its grammar should be reused.

The Librarian's primary learning artifact is the **Template Logic Card**.

# 9. Distinction Between Template, Pattern, and Component

## Template

A relatively complete visual arrangement designed to solve a recognizable class of problems.

Example:

`hierarchical_workflow_with_stage_clusters`

## Pattern

A reusable relationship or design rule extracted from one or more templates.

Example:

`primary_process_spine_with_secondary_evidence_clusters`

## Component

A reusable visual or interactive unit.

Example:

`StatusBadge`

## Composition Recipe

Instructions for assembling patterns and components for a particular visual problem.

Example:

```text
ROOT NODE
→ 4 DOMAIN CLUSTERS
→ child document nodes
→ cross-domain typed edges
→ semantic zoom
→ floating evidence inspector
```

This distinction is mandatory.

Otherwise the library degenerates into a warehouse of pretty rectangles.

# 10. Core Intelligence Tasks

The Librarian must eventually perform six distinct reasoning tasks.

## A. Classification

What kind of visual object is this?

## B. Decomposition

What structures, components, rules, and relationships compose it?

## C. Grammar Induction

Which observed patterns appear generalizable?

## D. Retrieval

Which existing grammars are relevant to this new request?

## E. Composition

How should compatible patterns and components be combined?

## F. Critique

Does the proposed output communicate the intended structure effectively?

These should remain separately testable services.

# 11. Learning Model

The initial system is not machine learning in the conventional model-training sense.

Version 1 uses:

* structured extraction;
* heuristics;
* embeddings/search where useful;
* comparison across Template Logic Cards;
* explicit rule accumulation;
* human correction;
* accepted/rejected recommendations;
* pattern frequency;
* contextual applicability.

Learning records should resemble:

```yaml
rule:
  statement: "Use semantic zoom when hierarchical node count exceeds the readable middle-view threshold."
  origin:
    type: human_correction
    run_id: RUN-0182
  applies_to:
    - mycelial_map
    - knowledge_graph
    - information_architecture
  confidence: 0.91
  status: adopted
```

A future statistical or learned model may use this accumulated corpus.

Version 1 should not pretend such training has already occurred.

# 18. First Version Success Criteria

The first Librarian is successful when it can:

1. ingest at least 10 structurally different templates;
2. generate valid Template Logic Cards for them;
3. identify repeated components across templates;
4. distinguish components from layout patterns;
5. distinguish layout patterns from complete templates;
6. accept one structured folder graph;
7. recommend at least three appropriate visual projections;
8. justify each recommendation;
9. produce a Visual Build Plan from a semantic request;
10. identify required components from its Component Registry;
11. state which components are missing;
12. preserve provenance for every recommendation;
13. accept user correction;
14. use that correction during a later comparable request;
15. produce the same visual plan deterministically when the same approved inputs and rules are used.

# 19. Governing Principle

> **The Librarian stores visual intelligence, not merely visual assets.**

Its deepest unit of value is not the frame, component, or template.

It is the recoverable relationship between:

**meaning → structure → visual encoding → interaction → reusable implementation.**

The key addition above is the explicit **projection layer**. Your Polytope work already requires one semantic object to remain identifiable across matrix, graph, timeline, canvas, and multidimensional views, so the Librarian needs to learn not only “templates” but *which visual grammar is appropriate for which projection problem*. 

# Deliverable 2 — Template Logic Card Schema v0.1

## Purpose

A `TemplateLogicCard` is the Librarian's canonical analysis object for a visual example.

It records not merely what a template looks like, but:

* what problem it solves;
* what information structure it expects;
* how it produces hierarchy;
* which visual relationships carry meaning;
* which components implement those relationships;
* which interaction rules govern it;
* when its grammar should and should not be reused.

A Template Logic Card is an analytical record.

It is **not** itself the Figma template.

# Governing Rule

> **A Template Logic Card describes the grammar that generated a surface, not merely the surface itself.**

That schema is intentionally capable of describing your folder mycelium and, much later, the Polytope. The latter needs matrix, graph, timeline, cross-selection, overlap, fold/unfold, and dimensional projection behaviors rather than merely a 3D renderer. 

# Deliverable 3 — Component Registry Schema v0.1

## Purpose

The Component Registry is the Librarian's reusable inventory of visual and interactive building blocks.

It must answer five different questions:

1. **What is this component?**
2. **What semantic job can it perform?**
3. **How does it behave visually and interactively?**
4. **Where can it be sourced or implemented?**
5. **Which templates and patterns can safely use it?**

A component is not defined merely by its appearance or source library.

For example:

```text
shadcn Card
```

is a source implementation.

```text
EvidenceCard
```

is a semantic component role.

The registry must distinguish them.

# Governing Rule

> **The Component Registry catalogs reusable visual behavior and semantic roles; source libraries merely provide implementations.**

That is what will let the Librarian choose intelligently between a Figma component, shadcn primitive, React component, Adobe asset, custom diagram primitive, or 3D object without mistaking any particular vendor for the architecture itself.

### What I would do in **Phase 2**

These three artifacts now give us three different layers:

```text
Product Brief
    ↓ defines WHY + boundaries

Template Logic Card
    ↓ defines WHAT THE LIBRARIAN LEARNS

Component Registry
    ↓ defines WHAT IT CAN BUILD WITH
```

The next logical deliverables are **4A: Visual Request Contract** and **4B: Visual Build Plan schema**. Those two form the compiler boundary between your Translator/Foreman and the Librarian. After that, I would make the **Folder Mycelium benchmark dataset** rather than doing more abstract architecture.

There is also a valuable constraint already embedded in your broader system: exploration should remain reversible, while promotion into canon is deliberate and provenance-bearing. That rule should govern Librarian learning just as strongly as it governs your Polytope and curriculum data.
